WMK Game Studio
Roadmap de evolução

Uma nova experiência para o GDevelop: organização de cenas e componentes inspirada em Unity, scripts e fluxos inspirados em Godot e edição JavaScript profissional com Monaco. O editor visual continua existindo, mas programar sem eventos visuais será uma opção completa e independente.

01. Visão do projeto

Missão: tornar possível desenvolver um jogo inteiro em JavaScript no GDevelop, começando em um objeto, anexando Robo.js, escrevendo start()/update(dt) e clicando em Play — sem abrir a aba Eventos.

2 modosVisual ou Código, independentes
1 motorGDJS e exportadores existentes
0 eventosObrigatórios no modo JavaScript
Princípio de produto: não criar um clone de Unity ou Godot do zero. Reaproveitar as bases maduras do GDevelop; alterar o fluxo de edição, o modelo de scripts e a ergonomia com compatibilidade.
  • Modo Visual: eventos, condições, ações e comportamentos do GDevelop, mantidos para compatibilidade.
  • Modo Código: arquivos JavaScript organizados por cena/objeto/componente, com ciclo de vida e API documentada.
  • Modo misto: projetos podem combinar os dois modelos sem exigir um do outro.
  • Meta de interface: painéis reposicionáveis, redimensionáveis, ocultáveis e layout restaurável, sem excesso de barras fixas.

O protótipo usa a variável interna __WMK_JAVASCRIPT_SOURCE, não um arquivo físico .js. Isso é um expediente temporário, que deverá ser substituído por um sistema de arquivos/recursos de scripts.

Primeiro caso de uso verificável

// Script anexado a spr_robo — API futura do WMK
export default class Robo extends WMK.Component {
  start() {
    this.velocidade = 180;
  }
  update(dt) {
    if (WMK.Input.isPressed('ArrowRight')) {
      this.object.x += this.velocidade * dt;
    }
  }
}

A sintaxe acima é o alvo de design, não uma API já entregue. A primeira versão experimental usa funções start()/update(dt) com variáveis object, runtimeScene e gdjs.

04. Arquitetura técnica proposta

WMK Game Studio (React / Electron)
  ├── Workspace e painéis gerenciáveis
  ├── Scene Tree / Inspetor / Assets
  ├── Script Explorer + Monaco + language service
  ├── Script Resource Manager (.js / referências)
  ├── Projetos: cenas + objetos + componentes + scripts
  └── Preview / Debugger
                │
                ▼
  Ponte de compilação e hot reload
  ├── Validação/importação de scripts
  ├── Cache por código + identificação do recurso
  ├── Bindings de objeto/cena/input/física
  └── Gerador de manifest para exportação
                │
                ▼
  Runtime GDJS (mantido e expandido)
  ├── Ciclo de vida por instância
  ├── Física / Animação / Renderização
  ├── Eventos visuais (opcionais)
  ├── Recursos / Prefabs / Cenas
  └── Exportadores Web / Windows / Mobile
Editor

Integrar Monaco como workspace completo, reaproveitando newIDE/app/src/CodeEditor.

Runtime

Evitar recompilar JavaScript a cada frame; isolar estado por instância; oferecer logs, tratamento de exceções e lifecycle.

Persistência

Substituir variável interna por recursos de script referenciados pelo projeto; definir import/export e migração reversível.

Segurança

Tratar scripts como código confiável; avisar ao importar projetos; evitar executar scripts de editor involuntariamente.

05. Roadmap por versões

Marcos são ordenados por dependência técnica. Versões são propostas; não são lançamentos disponíveis. Nenhuma data de entrega é prometida.

M0 • Protótipo experimental

v0.1 — Script anexado e Monaco

Parcial no PR #1

Provar que um robô se move apenas com JS anexado ao objeto.

Escopo e critérios
  • Selecionar spr_robo, abrir Script JS e anexar código.
  • Usar Monaco existente e ciclo start/update(dt).
  • Salvar, fechar, reabrir e executar sem evento da cena.
  • Testes isolados por instância, tipagem Flow/TypeScript, compilação Windows e smoke test.
  • Não liberar antes de demonstrar jogo real funcionando.
M1 • Fundação de scripts

v0.2 — Recursos .js e lifecycle sólido

Planejado • P0

Eliminar a variável interna provisória e separar script-fonte de instância.

Entregas
  • Arquivos/recurso de script com ID estável, referência por objeto e renomeação segura.
  • Importação, exportação, salvamento atômico, migração do protótipo e rollback.
  • Compilação em cache, erros por script/linha e comportamento seguro em hot reload.
  • start/update/onDestroy documentados; teste em preview e projeto exportado.
  • Compatibilidade com projetos existentes e sem script.
M2 • Fluxo de código

v0.3 — Modo Código em abas

Planejado • P0

Desenvolver sem jamais abrir Eventos.

Entregas
  • Explorador de Scripts, criação por objeto/cena, duplo clique e abas independentes.
  • Monaco amplo: temas, atalhos, snippets, busca, minimapa, formatação, fonte/zoom, localizar referências.
  • Indicadores de código alterado, salvar todos, histórico básico e tratamento de conflitos.
  • Comandos do editor: Novo Script, Anexar, Abrir, Desanexar, Duplicar e Localizar.
  • Teste de usabilidade: criar jogo apenas pelo fluxo Código.
M3 • Componentes

v0.4 — Modelo Unity + Godot

Planejado • P0

Múltiplos scripts e componentes por objeto, sem programação engessada.

Entregas
  • Componente/script com instância própria e parâmetros expostos no Inspetor.
  • Ordem de execução definida, habilitar/desabilitar e dependências entre componentes.
  • Componentes base: movimento, vida, inventário, interação, porta e coletável.
  • Composição e reutilização de objetos/prefabs; sinais e comunicação entre instâncias.
  • Exemplo: um robô com Movimento.js, Vida.js e Inventario.js.
M4 • Ergonomia

v0.5 — Workspaces livres e Inspetor

Planejado • P1

Interface profissional, leve e configurável.

Entregas
  • Árvore de cena, Inspetor, Console, Assets e Código como painéis movíveis/redimensionáveis.
  • Layouts salvos em JSON, presets: Código, Cena 2D, Depuração e Minimalista.
  • Busca de comandos, menus por categoria, atalhos e escala adaptável para telas pequenas.
  • Propriedades refletidas no Inspetor, edição de valores e sincronização com scripts.
  • Evitar excesso de painéis fixos; medir uso de memória em máquinas modestas.
M5 • Diagnóstico

v0.6 — Debugger e IntelliSense

Planejado • P0/P1

Identificar erros sem procurar mensagens perdidas no console.

Entregas
  • Definições TypeScript para WMK e GDJS; IntelliSense contextual por objeto.
  • Autocompletar e documentação em hover; exemplos verificáveis.
  • Breakpoints e mapeamento correto para código-fonte; pausas/step/variáveis e pilha de chamadas.
  • Console por instância e script, filtros de erros e relatório com linha/arquivo.
  • Profiler de CPU, alocação e tempo gasto em scripts.
M6 • Ecossistema

v0.7 — Eventos, física e módulos

Planejado • P1

API coesa para jogos reais, 2D primeiro e depois 3D.

Entregas

  • Sinais, colisões e eventos com semântica consistente.
  • Gerenciamento de módulos e dependências com empacotamento compatível com exportadores.
  • Biblioteca de exemplos: plataforma, top-down, puzzle, inventário e RTS mínimo.
  • Política de desempenho e compatibilidade entre web/desktop/mobile.

M8 • Release estável

v1.0 — WMK Game Studio

Meta de lançamento

Fluxo de desenvolvimento JavaScript completo, testado e sustentável.

Condições mínimas
  • Criar, executar, depurar, salvar e exportar um jogo 2D inteiramente em JavaScript.

07. Estratégia de testes, CI e desempenho

Testes unitários

Lifecycle, cache de script, estado por instância, carregamento, erros e migração.

Integração

Editor ↔ projeto ↔ runtime ↔ hot reload ↔ exportação; scripts combinados com eventos visuais.

E2E e visual

Fluxo criar objeto → anexar → digitar → salvar → Play; screenshots e regressão de layout.

Benchmark

Inicialização, memória e FPS com centenas de objetos com e sem scripts; comparar contra GDevelop base.

Pipeline sugerido: ESLint + Flow (IDE), TypeScript (GDJS), testes runtime, build web, build Windows e smoke test do jogo exemplo. Publicação de artefatos apenas quando as verificações exigidas passarem.

08. Riscos e decisões técnicas

RiscoImpactoMitigação
Alterar o runtime principalRegressão de jogos antigosMódulo isolável, feature flag inicial e testes de regressão
Usar new Function com código de projetoSegurança, CSP, depuração e empacotamentoTratar como código confiável no protótipo; migrar para pipeline de módulos compilados e mapas de fonte
Guardar fontes como variáveisProblemas de edição, exportação e versionamentoRecurso de script de primeira classe com IDs e migração
Dependência do código upstreamFork difícil de atualizarComponentes isolados, PRs pequenos e documentação de compatibilidade
UI pesadaPerda de FPS e alto consumo de RAMLazy loading de Monaco, limite de painéis e medição de memória
Dois modelos de programaçãoOrdem de execução ambíguaDefinir fases do loop e interop explicitamente
Decisão de prioridade: primeiro fazer o modo Código funcionar de ponta a ponta com um robô. Só depois ampliar a interface para novos workspaces, componentes e debugger avançado.
