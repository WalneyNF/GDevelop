WMK Game Data

Como salvar pontuações, progresso, inventário e estatísticas dos jogos usando JSON ou SQLite.

1. Como funciona

O jogo ou site envia dados JSON pela API HTTP local. O Game Store Manager escolhe o armazenamento configurado: JSON ou SQLite. As mesmas rotas funcionam nos dois bancos.

Jogo ou site → HTTP API → WMK Game Data → JSON / SQLite
JSONSQLite
Mais simples, ideal para protótipos, testes e jogos pequenos. Node.js 20+.Banco relacional em arquivo, com transações e índices. Node.js 24 recomendado.
Arquivo separado por jogo. Gravação substitui o arquivo completo.Arquivo SQLite separado por jogo, comandos SQL parametrizados.
Limites experimentais de 10 MB por arquivo e 5.000 registros por coleção.Melhor opção para persistência local. Não é, por si só, backend multiplayer público.

2. Primeira execução no Windows

Abra PowerShell na pasta do repositório. Os dados são armazenados separadamente dos arquivos do jogo.

cd D:\Ferramentas\WMK-Game-Studio\wmk-bridge
node --version
$env:WMK_ALLOW_WRITE = "true"
node server.js

O terminal informa a chave administrativa e o endereço padrão http://127.0.0.1:8767. A ponte só aceita conexões locais. Para dados de jogos, o MCP não é obrigatório; ele é necessário apenas para manipular o projeto aberto no editor.

Importante: não exponha a porta 8767 na internet, não publique tokens e não substitua a instalação do editor. Faça backups antes de escrever dados.

3. Escolher JSON ou SQLite por jogo

O padrão de cada jogo novo é JSON. Para escolher SQLite antes de gravar registros, faça uma solicitação administrativa.

$admin = "COLE_A_CHAVE_ADMINISTRATIVA"
$headers = @{ Authorization = "Bearer $admin" }
Invoke-RestMethod -Method PUT -Uri "http://127.0.0.1:8767/api/v1/games/meu_rpg/storage" -Headers $headers -ContentType "application/json" -Body '{"backend":"sqlite"}'

Para consultar a configuração: GET /api/v1/games/meu_rpg/storage. Para voltar a JSON num jogo ainda vazio, envie {"backend":"json"}.

A troca de backend é recusada quando o jogo já possui registros no banco de origem. Não há migração automática: isso evita perda acidental de dados.

4. Chave individual de cada jogo

A chave administrativa controla a configuração e gerencia credenciais. Uma chave específica de jogo acessa apenas aquele jogo, com escopo de leitura ou escrita. O servidor armazena o hash da chave e só mostra o segredo na criação.

POST /api/v1/games/meu_rpg/keys
Authorization: Bearer CHAVE_ADMIN
Content-Type: application/json

{"scope":"write","label":"Servidor do RPG"}

O retorno informa uma chave iniciada por wmkg_. Guarde-a em local seguro. Também existem as operações GET /api/v1/games/meu_rpg/keys para listar as chaves sem revelar segredos e DELETE /api/v1/games/meu_rpg/keys/{id} para revogar uma chave.

5. Endpoints disponíveis

RotaUso
GET /api/v1/gamesLista jogos (admin)
GET/PUT /api/v1/games/{game}/storageConsulta/configura JSON ou SQLite (admin)
POST /api/v1/games/{game}/keysGera chave (admin)
GET /api/v1/games/{game}Lista coleções
GET /api/v1/games/{game}/{colecao}Lista registros; aceita ?limit=100
GET /api/v1/games/{game}/{colecao}?stats&field=pontosContagem, soma, média, mínimo e máximo
GET /api/v1/games/{game}/{colecao}/{id}Lê registro
POST /api/v1/games/{game}/{colecao}Cria registro
PUT /api/v1/games/{game}/{colecao}/{id}Atualiza registro
DELETE /api/v1/games/{game}/{colecao}/{id}Exclui registro

As rotas do jogo exigem uma chave correspondente com escopo apropriado. O servidor também precisa de WMK_ALLOW_WRITE=true para aceitar alterações.

6. Exemplo prático: salvar pontuação

Exemplo JavaScript para testes somente locais:

const base = "http://127.0.0.1:8767/api/v1/games/meu_rpg";
const chave = "CHAVE_DO_JOGO_PARA_TESTES_LOCAIS";

async function salvarPontuacao(jogador, pontos) {
  const resposta = await fetch(base + "/pontuacoes", {
    method: "POST",
    headers: {
      Authorization: "Bearer " + chave,
      "Content-Type": "application/json"
    },
    body: JSON.stringify({ jogador, pontos })
  });
  if (!resposta.ok) throw new Error("Falha: " + resposta.status);
  return resposta.json();
}

async function ranking() {
  const resposta = await fetch(base + "/pontuacoes?limit=100", {
    headers: { Authorization: "Bearer " + chave }
  });
  if (!resposta.ok) throw new Error("Falha: " + resposta.status);
  return resposta.json();
}

Use coleções como pontuacoes, inventarios, progresso, conquistas e partidas. Os nomes são livres dentro das regras de validação.

7. Aplicação web de estatísticas

É possível criar uma página HTML que exiba ranking e estatísticas dos jogos, mas não coloque a chave de jogo no JavaScript público. Num jogo publicado, seu backend precisa autenticar os jogadores e guardar a chave no servidor.

Navegador do jogador → Backend autenticado do criador → WMK Game Data → Banco JSON/SQLite

As rotas atuais destinam-se a experimentação local. Não implementam contas de jogadores, ranking antifraude ou HTTPS público.

8. Segurança, limitações e próximos recursos

Já implementado: acesso local, tokens separados, chaves por jogo e escopo, revogação, validação de identificadores e SQL parametrizado.

Ainda planejado: backup automático, migração JSON↔SQLite, autenticação individual de jogadores, controles por coleção, rate limiting, monitor de consultas, auditoria e dashboards públicos protegidos.

9. Testes

node --test wmk-bridge/tests/*.test.js

O workflow WMK Game Data - Testes JSON e SQLite executa testes reais de persistência, chaves, escopos e isolamento com Node.js 24. Verifique o resultado no GitHub Actions para a versão utilizada.
